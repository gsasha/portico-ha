# transport-rs parity: WebRTC and the SFU

Scope: `internal/sfu` (the pure audio code, the str0m session) and `internal/call` (the sequencer, the relay registry, `webrtc_*`).

The numbered differences of the whole port are indexed in [../../PARITY.md](../../PARITY.md); their numbers are stable (code comments, tests, the review log and the contract map cite them), so a new difference takes the next free number of its range and goes into the file of its subject. "Smoke" means `scripts/ipc_smoke.py` gave byte-identical output on both binaries, "unit" means a `cargo test` case. Reference: Go `transport/` at the branch point of `dev-764-rust-skeleton` (main `a52af72`), built with `golang:1.23`. Long table cells are shortened to a summary with the full text below the table.

### G.722: how it is ported, and why

Go's `g722.go` imports `github.com/gotranspile/g722` (`cxgo` translation of Steve Underwood's `g722_encode.c` / `g722_decode.c` as repackaged in `dgoncharov/g722tools`; its README: "Distributed under the BSD license ... Steve Underwood ... public domain"). `src/sfu/g722.rs` is a hand port of that Go code, `Rate64000` / flags 0 only (no 56/48 kbit/s, packed, 8 kHz or ITU-test modes: the SFU never builds those). No crate was used: nothing to pin, and bit-exactness against THIS Go output is what counts (a crate would still have needed the same proof). Go's `int` is 64 bits and the port uses `i64` with the same three narrowings (`int32` in `saturate`, `int16(...)` stores, `uint8(int8(code))`). The two copies of `block4` in Go (`encodeBlock4`, `decodeBlock4`) are identical in effect and share one function here. Proof: the golden vectors above, every byte equal; deliberate mutations of a QMF coefficient and of the step-size update each fail the replay.

### Go oddities found (ported, not fixed)

* **Odd G.722 frames kill the process** (difference 55). Not reachable with the hub's frames.
* **The uplink gate compares the packet's WIRE payload type with the static 9 and 0** (`readRemoteTrack`), while the answer echoes whatever payload types the offerer used. A peer that offers G.722/PCMU under dynamic types (the answer then names `96 97`, recorded: "g722 and pcmu on dynamic payload types 96 97") is answered, connects, and every packet it sends is dropped as foreign, counted and logged once at the end. Read from the code (a real session was not run with such a peer). Browsers use 9 and 0.
* The policy is pion's, not a decision: a `G722/16000` rtpmap on payload type 9 changes nothing (the static table wins), a dynamic `G722` with no clock rate is dropped (default clock 90000), PCMU with two channels is dropped, an `fmtp` line is echoed into the answer, a payload type in the `m=` line with no codec is an error for the whole offer. Recorded as vectors.
* `SetSilence` after the first `Push` does nothing (documented by Go's comment); the G.722 silence byte is therefore set before the push, by the first packet, only if it is G.722.
* `g722SilenceByte` (0xFB) is "the byte a fresh encoder emits for digital silence" and decodes to a very quiet signal, not silence (`TestG722SilenceByteDecodesToNearSilence` allows a peak of 300).
* The downsampler is a 2-tap box filter (aliasing above 4 kHz); documented in Go and kept: the PCMU leg folds a 6 kHz tone down.
* Overflow keeps the FIRST 8 frames and drops the later ones (`forward` drops what does not fit), the opposite of dropping the oldest.
* PLC: there is none in `internal/sfu` (a lost slot is the silence byte). Nothing to port.

### Not verified (4a)

* **Timing.** The uplink scripts ran in real time on the Go side (the sleeps and the 5 ms margin of the playout-delay pins), on an idle host; three regenerations were byte-identical, the Rust replay runs on a paused clock. A loaded host could move a Go frame across a window edge when regenerating.
* **The policy model against pion for offers it has not seen.** 43 offers (pion-written, hand-edited, two real browsers) agree; the model is not proven for every SDP. No Safari or phone-app offer exists in the repository.
* **The first-codec-wins gate, the RTP counters and `bind_codec`** are ported from reading `sfu.go` / `g722.go`, with unit tests that assert what the code says; no Go run backs them (they are inside the `pion`-bound goroutines).
* **G.722 modes other than 64 kbit/s, 16 kHz, unpacked** are not ported and not tested.
* The sandbox has no browser audio: nothing here says how the audio SOUNDS; the tone tests measure frequency, level and gaps like Go's.
* Rust `sip::JitterBuffer` under the uplink wrapper uses the paused-clock scheduler in tests; under a multi-threaded runtime the order in which `forward` and the reader wake is not pinned.

### Go oddities found (ported, not fixed)

* **A failed `webrtc_offer` leaves its session in the registry.** `getOrCreate` registers the session before `HandleOffer` runs; a failure (garbage SDP, Opus only) is returned but the session stays, with no ICE state, so `OnDisconnected` never fires and nothing removes it (a leak). The follow-up `webrtc_ice` / `webrtc_answer` then get `remote description is not set` / the stable-state text. transport-rs does NOT keep this (difference 79): the session is dropped at once and the follow-ups are `unknown_session`.
* **The uplink buffer is hypersensitive to its tick phase and loses a slot about every second to a sender whose clock runs fast (found by the interop runs; not fixed, it is the Go algorithm).** `pkg/sip.JitterBuffer` plays a slot every 20 ms from `first push + delay` and admits a packet only if its sequence number is within 9 frames of `nextSeq` (3 x the 60 ms delay). Headless Firefox sends 50.7 packets a second against the buffer's 50 (761 packets in 15 s): the buffer fills until the window is full, every packet beyond it is refused as an "outlier", and the slot it would have filled is played as silence, about 0.7 a second. A lost G.722 slot is worse than a lost PCMU one: the decoder's predictor is out of step and takes 2 to 5 frames (40 to 100 ms) to settle (measured: rms of the decoded tone dips for 3 to 5 chunks of 20 ms). On top of that the loss depends strongly on the PHASE of the ticks against the arrival stream: replaying three recorded arrival traces through a model of Go's buffer (a Python model of `admitLocked` and `playoutLoop`, run on the recorded traces) with the tick phase moved from 0 to 20 ms gives between **13 and 172 silent slots of about 760** for the same packets (the same traces through the real Go buffer in real time: 9 to 24). Live, with the same Firefox and harness (scenario H3, 15 s, six runs each; the count is 20 ms chunks of the decoded tone below half level inside the call, which includes the 5 every call loses to its first resync): Go 6, 23, 23, 44, 48, 50 (median 34); Rust 5, 27, 36, 38, 43, 53 (median 37) once the playout clock is anchored to the first push (difference 77). Before that change the Rust figures were bimodal: 18 runs gave 5 to 15 or 47 to 169, nine of them above 45 and three above 100 (a 300 ms hole every second). Consequences: in a real call the device hears an occasional glitch (about once a second in the worst phase, a 100 ms dip each), and the interop criterion "the station hears the browser's tone in 70 % of the windows" fails in a few runs (INTEROP.md). A better buffer (adapt `nextSeq` to the sender's clock, or drop the OLDEST packet when the window is full instead of refusing the newest) is a change to the shared `sip::JitterBuffer` and to Go, so it is recorded for DEV-770, not made here.
* `webrtc_ice` with `a=end-of-candidates` is an error in pion; the empty string is the accepted form.
* `webrtc_answer` can never succeed: the only offerer is the browser.
* The pion error texts include Go-internal names (`InvalidStateError`, `InvalidModificationError`); they are reproduced because Python may log them.
* A 1 MiB IPC line ends the process (slice 1 oddity); a large offer therefore never reaches `webrtc_offer` above ~1 MB, and the 64 KiB cap is far below it.
