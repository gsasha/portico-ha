# transport-rs parity: dahua_sip driver

Scope: the `dahua_sip` driver (`pkg/driver/dahua`) and the relay path of `internal/call/relay.go`.

The numbered differences of the whole port are indexed in [../../PARITY.md](../../PARITY.md); their numbers are stable (code comments, tests, the review log and the contract map cite them), so a new difference takes the next free number of its range and goes into the file of its subject. "Smoke" means `scripts/ipc_smoke.py` gave byte-identical output on both binaries, "unit" means a `cargo test` case. Reference: Go `transport/` at the branch point of `dev-764-rust-skeleton` (main `a52af72`), built with `golang:1.23`. Long table cells are shortened to a summary with the full text below the table.

## dahua_sip and the relay (slice 6)

Reference: Go `transport/pkg/driver/dahua/dahua.go` (328 lines) and its tests (`dahua_test.go`, `pending_test.go`), `transport/internal/call/relay.go` (188 lines; `relay_test.go`, `relay_host_test.go`), and the pending-ring half of `cmd/portico-transport/main.go` (`pendingRinger`, `findPendingRing`, `relayRegistry`, `relayClosingSink`, the `findPendingRing` branch of `joinCallToBrowser`, the `-host` flag). Go drift check (`git log a52af72..origin/main -- transport`, re-run at the start): only the sfu G.722 PR #282, the observer commits `9ec8271` / `fe4dafe` and the `ha_event` ring, all ported earlier; nothing newer in the dahua or relay files. Code: `src/driver/dahua/mod.rs`, `src/call/relay.rs`, `src/webrtc.rs` (`RelayRegistry`, `RelayClosingSink`, `find_pending_ring`, `join_call_to_browser_with`), `src/dispatch/mod.rs` (`register_full` takes `-host`, the registry sink is `RelayClosingSink` over `DeviceSink`, `ErrorReporter`), `src/driver/mod.rs` (`PendingRinger`, `ErrorReporter`, `EventSink::error_reporter`).

What Go's dahua driver is: a SIP user agent. `Start` opens one `sip.Endpoint` to `host:5060`, registers `sip_user`/`sip_password` (`8001#1`) and reports an inbound INVITE as `ringing` (180 with a stable To-tag, retransmits deduped), a CANCEL as 200 + 487 + `ended`, a BYE as 200 + `ended`. `Answer` accepts the ring offering the hub's media target; `Dial` INVITEs the device; `PendingRing`/`PendingRingFor` hand the ring to the relay path, which answers it only after the browser connected, on a real RTP socket opened BEFORE the SDP is built. `OpenRelay` always fails (the text is Go's, verbatim, with its em dash). The driver has no port setting (always 5060); the tests use a package variable (`sipPort`), here the `SIP_PORT` seam and `Dahua::set_sip_port`.

**Row 102, Rust column, in full.** a panic in the registration task is caught by its supervisor: logged with the payload, `driver_availability` goes false (`internal error`) so HA stops showing the device available, and the registrar is started again with a backoff (5 s doubling to 5 min; `Stop` or the hub's context during the wait ends it at once and the stop latch is then set). No new error code is invented, and no `driver_error` is raised for a panic (it is not terminal). A panic in a SIP handler is caught by the endpoint's dispatcher (slice 2) and the next request is served **No de-REGISTER on that path (R2-120):** when the registrar panicked while it was registered and `Stop` (or the hub's context) arrives during the restart wait, the loop ends without a de-REGISTER, so the device keeps its session-quota slot until the registration expires. Go's panic ends the process and leaves the same slot, so it is not a parity gap; the registrar of the restarted run does not exist yet, so there is nothing to de-register with.

### Go defects found (kept in the port; for DEV-770)

* **A ring taken by a browser offer cannot be CANCELled.** `PendingRingFor` consumes the ring at offer time, before the browser connects. If the station then CANCELs (the visitor gave up, or the browser never connects), the CANCEL handler finds no pending ring and answers 481, the INVITE never gets its 487, and no `ended` reaches Python: the call stays "ringing" in HA until the station's own timeout and the offer's session. Pinned by the golden scenario `ring: taken by an offer ...` and by `a_cancel_after_the_offer_took_the_ring_is_481_with_no_ended_as_in_go`. Candidate fix: keep the ring (and its tag) until it is answered or CANCELled, and let CANCEL end it either way.
* A browser that never connects after taking the ring leaves the INVITE unanswered with no 487/480; a second offer for the same call finds no ring.
* A direct `Answer`/`Dial` call is stored in `activeCall`, which nothing reads: the IPC `hangup` finds no `CallHangupper` among the dahua drivers (`not_implemented`), `Stop` sends no BYE for it, and a second `Dial` overwrites the first dialog without ending it.
* The BYE handler answers 200 and reports `ended` for ANY Call-ID, including calls it never saw, and clears `activeCall` for any BYE.
* An INVITE with no `Call-ID` header is never a ring on a fresh driver (the empty id equals the initial empty `ringCallID`); after a BYE clears `ringCallID` the same holds again. Pinned by a golden scenario.
* `Capabilities.HasRelay` is true while `OpenRelay` always fails.
* The 200 OK to the station's INVITE is never retransmitted until an ACK arrives (RFC 3261 13.3.1.4), and INVITE retransmits after the answer are ignored: a lost 200 leaves the call half-open.
* A ring whose INVITE has no SDP body is never answered or rejected (`Answer` fails and consumes it; the station keeps ringing).
* A second INVITE with a new Call-ID silently replaces the pending ring (no 486/487 for the first).
* `DialDevice` / `AnswerDevice` hold the answered dialog only from the point the leg is published; a future dropped earlier leaves the call up (Go the same; Rust's `ByeOnDrop` covers it only from the start of `install`, so the window between `answer_incoming` returning and `install` starting is still unguarded, with no `.await` in it for a dropped future to land in).
* A dead relay stays registered if the station BYEs between `answer_incoming` and `relays.put`; it lingers until the browser leaves (Rust the same).
* `mediaHost` accepts IPv4-mapped IPv6 (difference 99); `Relay.Close` is not idempotent (difference 100); `Dial` before `Start` panics (difference 101); a second `Start` leaks (difference 98).
