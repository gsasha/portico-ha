# transport-rs parity: gate_sip_server driver

Scope: the `gate_sip_server` driver: the driver interface family and the configuration core (3a), the server loop (3b-1) and the outbound call (3b-2).

The numbered differences of the whole port are indexed in [../../PARITY.md](../../PARITY.md); their numbers are stable (code comments, tests, the review log and the contract map cite them), so a new difference takes the next free number of its range and goes into the file of its subject. "Smoke" means `scripts/ipc_smoke.py` gave byte-identical output on both binaries, "unit" means a `cargo test` case. Reference: Go `transport/` at the branch point of `dev-764-rust-skeleton` (main `a52af72`), built with `golang:1.23`. Long table cells are shortened to a summary with the full text below the table.

## pkg/driver and gatesipserver core (slice 3a)

Reference: Go `transport/pkg/driver` (`driver.go`) and `transport/pkg/driver/gatesipserver` (`config.go`,
`media.go`, `audio.go`, `driver.go`, and the `AudioClient` half of `server.go`) at the branch point of
`dev-764-rust-driver-core`. Not in this slice: `server.go` (SIP/RTP loop) and `dial.go`; see "slice 3b tests".
Evidence: "golden" = a vector from the real Go code replayed in `tests/golden_driver.rs`, "port" = a ported Go
test (Go name in a comment). The unexported Go functions (`parseConfig`, `config.allowed`, `chooseMedia`,
`sdpFor`, the A-law and converter functions, `newCallAudio`, `closeLocked`) are called by the generator through
`//go:linkname` (nothing in `transport/` is edited); the `Server` and `AudioClient` of the audio scripts are the
real exported types with their unexported fields set by reflection, and the generator copies the 4-line
non-blocking push of `rtpLoop` (the one piece of `server.go` the audio scripts need) and counts it itself.

**Row 30, Why column, in full.** no Go resolver; not reproducible in a golden vector (the only name used is `localhost`). glibc also accepts the `inet_aton` shapes (`127.1`, `0x7f.1`, `2130706433`, `0177.0.0.1`) that Go refuses, so Rust refuses any host of one to four decimal/`0x`/octal numbers before resolving: `lookup X: no such host`. ### Go oddities (ported, not fixed)

* `rtp_port`, `ring_seconds`, `orphan_seconds` present as JSON `null` are an error, but `dial_enabled: null` means off and `allow_from: null` is "must be a list".
* The password length is in BYTES (`len`) but the message says "characters": five `é` (10 bytes) pass, eight `é` (16) fail with "password is 16 characters". `TrimSpace` silently strips a padded password, so the station gets a different one than typed.
* `allow_from: []`, or only blank entries, is accepted (an empty list means "everyone" on loopback).
* An IPv4-mapped IPv6 PREFIX (`::ffff:10.1.2.0/120`) stays IPv6 and can never match an address, because `allowed()` unmaps the candidate first; a bare mapped address is unmapped, so only the prefix form is dead.
* `sip_listen` is kept verbatim: `127.0.0.1:` (port 0), `127.0.0.1:+5060` and `127.0.0.1:-0` are valid and end up in the default `device_id` as written. `127.0.0.1:12a` is an unknown port; the name `domain` is accepted.
* `010.0.0.1:5060` is not an IP to `netip` (leading zero), so it is looked up as a host name and fails `no such host`.
* Resolving a host name in `sip_listen` happens inside `Configure` and may block the configure handler; the address Start later binds is the string, not the resolved IP.
* `chooseMedia`: `\s+` spans newlines, so `m=audio 5004 RTP/AVP` with no payloads takes the NEXT line of the SDP as its payload list (and echoes it in the "nothing we speak" note, `\r` included); an `a=rtpmap` name may contain a newline; a name of whitespace only (`a=rtpmap:96   /16000`) is accepted.
* `applyGain` returns its input untouched (odd trailing byte included) for gain <= 1; the driver always uses 4.
* After the call ends, a writer to `CallAudio.In()` fills the 16-slot buffer and then blocks forever (difference 25).
* `callAudio.Detach()` is `AudioClient.Goodbye()` (BYE at once) while `AudioClient.Detach()` is the orphan-grace path; the name is the same, the behaviour is not.
* `Driver.Answer` returns the package's own `ErrAlreadyAnswered` / `ErrNoCall`, not `driver.ErrAlreadyAnswered`, so the IPC code is `answer_failed`, never `already_answered`; only `AnswerWithAudio` maps to the driver sentinel.

### Server loop (slice 3b-1): Go oddities found (ported, not fixed)

* `Hangup()` sends a BYE even for a call that was never answered: on a RINGING call it BYEs the unanswered INVITE (a 480/487 is what the station is owed; `HangupCall` and the orphan timer do require an answered call). Golden scenario "hangup with a call nobody answered".
* `REGISTER` ignores `Expires`: `Expires: 0` (a de-registration) is registered like any other and answered `Expires: 300`. Read from the code, not exercised. **Not ported: difference 45.**
* BYE, CANCEL and ACK are matched on Call-ID only: any allowed source that knows (or guesses) the live Call-ID ends the call; the dialog tags are not checked. **BYE/CANCEL: not ported, difference 44** (ACK still matches on Call-ID only, tags are still not checked).
* `rtpSourceOK` does not require the call to be answered: RTP is counted (`RTPIn`) and queued during the ring.
* The `Stats.Registered` comment says "set on ANY REGISTER, digest pass or fail"; the code sets it only on a digest pass.
* A `c=IN IP4` line holding an IPv6 literal is accepted (the family is not checked); the answer SDP prints `c=IN IP4 <v6>` for a station that connected over IPv6.
* A retransmitted INVITE gets a fresh 100 and 180/200 every time, with no rate limit (any allowed source can make the server send two datagrams per datagram).
* A media port over 65535, or too many digits for an int64 (read as 0), leaves the call answered with no RTP ever sent and no error (kept on the wire; Rust logs and counts it, difference 48).
* `d.Start` leaks one goroutine per call with a context that never ends.
* `OPTIONS`, `401`, `403` replies mint a new random `To` tag every time.

### Outbound call (slice 3b-2): Go oddities found (ported, not fixed)

* `Hangup()` of a call still ringing out clears the slot and BYEs the unanswered INVITE (no To tag yet); the `DialCall` that placed it **keeps waiting**: the station's answer is dropped (the slot is no longer its call) and it ends only at the ring timeout (then a CANCEL for a dead dial) or at `Stop`. Golden scenario "Hangup while the INVITE rings out".
* The codec check accepts anything `chooseMedia` calls wideband or narrowband, not only what was offered: an answer of `L16/16000` under payload 100, or `PCM/16000` under another number, brings the call up (and RTP is then sent under that payload type). Offered: 96 PCM/16000 and 8 PCMA/8000.
* In `answered`, if the slot was cleared between the 200 and the checks (`Hangup`, `Stop`), the function returns `ErrServerStopped` after the ACK and sends no BYE: the station believes the call is up until its own timers end it.
* A retransmitted 200 is ACKed again with no rate limit, per datagram (like the retransmitted INVITE, sip defect 6).
* An answer whose SDP names a media port over 65535 or with too many digits is refused ("named no media port"); an INVITE with such a port is answered (3b-1 oddity). Not the same rule on both sides.
* The `ended` of a dialled call is emitted by whoever clears the slot; a call cleared by `Hangup()` while still ringing out reports nothing at all, and neither does the later `DialCall` failure (it returns an error nobody maps to an id).

### Outbound call (slice 3b-2): not verified

* **Timing.** Like 3b-1: the dial scenarios run on real time (windows 120 to 450 ms, ring 300 to 5000 ms, caps 250 to 300 ms); two Go regenerations were byte-identical and the Rust replay passed in 6 of 6 runs here on an idle host. A snapshot is only taken where the 20 ms RTP counter cannot race (`rtp_out_positive` after a read of the server's own RTP). Nothing was run under load.
* A real Dahua station: no capture exists. In particular whether the real station sends its 401 for the INVITE (the code answers it as gate-sip does) and from which address its BYE comes (difference 44/52 assume the address it was INVITEd at).
* IPv6 stations (the request-URI is `sip:9901@<ip>` without brackets, as in Go), the 407 path against a real proxy, a `qop=auth` challenge for the INVITE (the digest comes from the ported `AuthorizationFor`; the goldens use no qop because its `cnonce` is random).
* The drop guard under a multi-threaded runtime; with no runtime at all it sends the CANCEL and frees the slot at once and does not wait for the final answer.

## Known flake: golden_server_scenarios under host load

`tests/golden_server.rs::golden_server_scenarios` replays real-time transcripts recorded from the real Go server (windows of 120 to 450 ms, ring timeouts of 300 to 5000 ms on the real clock, no fake clock on the Go side). While another job kept the host at load average about 6.6 (a Gradle/Kotlin build of the Android app), it failed at `tests/golden_server.rs:930` in two of four full-suite runs of the slice 4b commit; run alone it passed 3 of 3 under the same load, and a full run with `--no-fail-fast` later passed all 348 tests. So it is timing sensitivity, not a regression. Consequences: (1) do not read a single red run of this one test as a regression, rerun it alone first; (2) CI needs a retry or a quiet runner; (3) follow-up: scale the replay windows by a measured load factor, or move the Rust side to a paused clock where the transcript allows it. The same sensitivity applies to any scenario whose ring/orphan timers run on the real clock (`server_parity`, `server_dial`, `rehearsal`), which passed in every run so far.
